# Inventory: klibs.io as a KDM consumer

What [klibs.io](https://klibs.io) is, what it would need from KDM and from the renderer,
and what that changes in the requirements we are gathering now.

Like `50-extension-points.md`, this file is **descriptive**: it records the consumer and
the questions it raises (Q-040…Q-047). It decides nothing. No ADR yet — too little
context, by the owner's call.

Status of implementation: **not v1.** The point of writing this now is that the model is
a published, compatibility-constrained artifact (`README.md`), so klibs.io's requirements
on *KDM* must be known before KDM freezes, even though the *integration* ships later.

---

## 1. Scope, as decided

Of the possible uses of KDM on klibs.io, the owner's ranking:

| Use | In scope |
|---|---|
| Hosting API reference for indexed libraries | **yes — primary** |
| KDM behind klibs.io's public API / MCP server | yes |
| Search by API (declarations, signatures) | undecided |
| Registry of KDM artifacts / external link resolution | undecided |
| Cross-version API diffs | **out of scope** |
| Doc-coverage metric (`reportUndocumented` as a consumer tool, Q-011) | not discussed; cheap, see O-70-04 |

Where KDM comes from, as decided:

1. **Downloaded from Maven Central**, when the library publishes it. Primary path.
2. **Submitted directly to klibs.io** by the author. Secondary, an extra affordance.
3. **Generated by klibs.io itself — explicitly ruled out.** Download limits on Maven
   Central make bulk jar retrieval impossible, and klibs.io has no analysis capability
   (§ 2).

## 2. What klibs.io is today

Confirmed from the repository (`JetBrains/klibs-io`, Apache-2.0, Spring Boot + Next.js)
and public docs. This section is the *ground truth* the requirements must fit.

- A catalog of **Kotlin Multiplatform libraries**; >4,200 projects, launched Dec 2024,
  owned by the JetBrains Kotlin Websites team.
  [Launch post](https://blog.jetbrains.com/kotlin/2024/12/introducing-klibs-io-a-new-way-to-discover-kotlin-multiplatform-libraries/) ·
  [FAQ](https://klibs.io/faq) · [docs](https://kotlinlang.org/docs/multiplatform/klibs-io.html)
- **Unit of listing is a GitHub project**, grouping its Maven packages
  (`klibs.io/project/<owner>/<repo>`). Schema: `project` → `package` (1:N) →
  `package_target(platform, target)`.
- **It crawls the Maven Central index** (plus Google Maven). It **does not build,
  compile, or read `.klib` / class files**; there is no compiler, Analysis API or Dokka
  dependency anywhere in the repo. Targets come from `kotlin-tooling-metadata.json`,
  which is also the inclusion criterion.
- Search is project- and package-level only (Postgres FTS, an OpenSearch path is
  appearing). **Nothing in the schema represents a declaration, signature or KDoc.**
- READMEs are stored in **S3 with a local disk cache** — the precedent for storing
  generated artifacts.
- A live, unauthenticated **MCP server** at `https://api.klibs.io/mcp` with exactly two
  tools: `searchProjects`, `getLatestVersion`. Nothing documentation-shaped. Plus an
  agent skill `kmp-libraries-expert` and [klibs.io/ai](https://klibs.io/ai).
- No documented public REST API (`/v3/api-docs` → 401) and no dataset dump.
- The only docs-adjacent link on a project page is **"GitHub pages"**, driven by
  `scm_repo.has_gh_pages`. For many libraries it happens to point at Dokka output —
  klibs.io does not know that.

### Prior art and commitments already on record

- **KEEP-0460 (KDM)** names klibs.io as a canonical consumer throughout: "source of truth
  for documentation tooling, including the first-party HTML renderer, klibs.io, IDEs";
  architecture diagram `mc -.-> klibs`, `klibs -.-> renderer`; "a bundled renderer also
  lets klibs.io serve consistent rendering for any library that publishes the model";
  "aggregation across multi-module projects belongs to the model consumers"; "klibs.io
  aggregation depends on a shared notion of declaration identity".
  [KEEP #484](https://github.com/Kotlin/KEEP/discussions/484)
- **OSIP-1305 [Meta] KDM** lists as a strategic enabler: *klibs.io (docs hosting,
  cross-library search, API diff, doc coverage)*, with OSIP-1047 as a dependency.
- **OSIP-1047** "Prototype auto-generated API reference documentation for KMP libraries
  on klibs.io" — **Postponed**, reason: *"requires Dokka team involvement, postponed
  until the IR implementation is ready (aka Dokka 3.0)"*. We are the blocker.
- **KTL-4815** (this work) already asks how the renderer "is executed within the Kotlin
  toolchain **and on the klibs.io backend**", and whether the **FQN→URL external link
  resolver should be extracted as a shared component for klibs.io** → Q-044.
- Publicly, from klibs.io's side, there is only
  [issue #84 "Support KDocs hosting"](https://github.com/JetBrains/klibs-io-issue-management/issues/84)
  (May 2025, open, unassigned, no comments) — and it proposes picking up **javadoc jars**
  from Maven Central. Neither Dokka nor KDM is mentioned. See O-70-05.

## 3. Observations

`O-70-##`, local to this file.

- **O-70-01 — klibs.io adds no gate to the stack; it adds one execution target.**
  `stack-criteria.md` gates K-01 (no node/npm on PATH), K-02 (JDK 8 baseline), K-03
  (full OS/arch matrix) and K-04 (offline/hermetic) all describe the *user's build
  machine*. On the klibs.io backend every one of them relaxes: Node is present (Next.js
  frontend), JDK 21+, one platform, network available. What klibs.io does add is a target
  the document does not currently contemplate at all: **the browser** (Q-041).
- **O-70-02 — the SPA question is already open, and klibs.io is what settles it.**
  `stack-criteria.md § 1`: "the output must be a set of static HTML files; an SPA variant
  may exist in addition, but is not required", surviving as **K-44** and **Q-036** ("is
  an optional SPA output actually wanted, or merely tolerated?"). Because K-44 is scored
  in the weighted survey, **Q-040/Q-041 must be answered before any stack spike**, not
  after.
- **O-70-03 — the page/URL layer is already portable.** `kdm-pages` is deliberately plain
  `kotlin("jvm")` and its README states that moving the logic to `commonMain` "is a
  directory move if the browser ever needs it". Whatever Q-041 decides, this stays the
  cheap part; the expensive part is an isomorphic *view* layer.
- **O-70-04 — doc coverage is the one use that needs no renderer.** Percentage of
  documented public API per package/version is computable from KDM alone and slots into
  klibs.io's existing library-score work (`scm_repo_health_components`, KTL-4557/4562).
  It is therefore the cheapest possible end-to-end proof of the KDM → klibs.io path.
  Re-weights **Q-011**.
- **O-70-05 — there is a cheaper competing path, and it does not need us.** Issue #84
  (javadoc jars) is available to the Websites team today. If KDM has no date, klibs.io
  plausibly ends up hosting *existing Dokka HTML* rather than consuming KDM — which
  satisfies "hosting" while foreclosing everything else in § 1. This is a scheduling
  risk, not a technical one.
- **O-70-06 — discovery and download are separable.** The Maven Central index lists
  classifiers and extensions, so "does this version publish KDM?" is answerable *from the
  index*, without fetching the artifact — the same place klibs.io already learns about
  `kotlin-tooling-metadata.json`. The download limit therefore constrains **artifact
  size**, not discovery (Q-046).
- **O-70-07 — the aggregation unit does not match.** klibs.io aggregates by GitHub
  project (N Maven packages, e.g. Arrow's dozens); KDM arrives per module, from separate
  artifacts, possibly published at different times with different versions. ADR-0002
  already assumes multi-module input, but there the set is consistent *by construction*
  because it comes from one build. Here it is not (Q-045).
- **O-70-08 — "API search: undecided" and "KDM in API/MCP: yes" are the same requirement
  at different depths.** Both need a per-declaration index, which klibs.io does not have
  (§ 2). Handing an agent a 3–30 MB blob is not a product; the moment point queries are
  wanted, 80% of signature search exists (Q-047).
- **O-70-09 — hosted docs that need JS to read undercut klibs.io's own purpose.**
  klibs.io exists for discovery; API pages invisible to search-engine and LLM crawlers
  subtract from that. This makes `stack-criteria.md` Q-032 ("does *static HTML* mean
  readable with JS disabled, or only servable without a server?") a klibs.io question,
  not only ours (Q-043).

## 4. Requirements this consumer places on KDM

Candidates for `60-model-gaps.md`, stated here first because they came from this consumer
and none of them is currently in that file.

| # | Need | Because | Related |
|---|---|---|---|
| R-70-01 | **Artifact self-description**: KDM schema version, Kotlin version, coordinates, produced-at — readable without joining against anything else | A consumer assembling artifacts from Maven Central must be able to *refuse* an incompatible or inconsistent set | Q-045, Q-046 |
| R-70-02 | **Artifact size budget as a number** | `KDM spec.md` already reports 1 MB / 3 MB / 30 MB for CK core depending on the deduplication scheme. At 4,200 projects × versions, the difference between 3 and 30 MB *is* the answer to whether hosting is viable | Q-046, Q-017 |
| R-70-03 | **Declaration identity strong enough to be a network contract** | A shared FQN→URL resolver only works if an id computed in someone's build equals the id on klibs.io. Today ids are measurably not unique (`jvm/main`: 238 elements, 132 unique ids, 3 structural collisions) | **G-01**, Q-013, Q-044 |
| R-70-04 | **Published coordinates / classifier convention** for the KDM artifact | It is a public contract the moment klibs.io reads it from the index. Turns **Q-006** (KDM vs `kdp` naming) from cosmetic into blocking | Q-006, Q-046 |
| R-70-05 | **Provenance / completeness marker** per artifact, if a degraded producer is ever allowed | Author-submitted (§ 1.2) and Central-published KDM may differ in completeness; without a marker klibs.io silently presents partial docs as complete. Same hole as **Q-025**, one level up | Q-025 |
| R-70-06 | KDM must **not** be shaped for rendering convenience | It is the source of truth (KEEP-0460). Anything presentation-shaped belongs to a separate artifact owned by the renderer | Q-042 |

## 5. Requirements on the renderer

| # | Need | Because |
|---|---|---|
| R-70-10 | An entry point **"a set of KDM artifacts → a site"**, not "the output of one build" | O-70-07; also the "execution on the klibs.io backend" question in KTL-4815 |
| R-70-11 | Tolerate an **inconsistent** input set (missing modules, mismatched versions) and degrade legibly | Artifacts arrive independently from Maven Central |
| R-70-12 | FQN→URL as a **pure, shareable function** over (coordinates, element id) | Q-044; a build-time network call would violate gate K-04 |
| R-70-13 | Per-declaration projection (id, signature, short description) available as data, not only as HTML | O-70-08; possibly the same artifact as Q-042 |
