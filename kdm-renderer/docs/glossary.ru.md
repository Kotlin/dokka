# Словарь и понятия

> Русская версия [`glossary.md`](glossary.md). Ведущая копия — английская: она входит в
> обсуждение [KEEP #484](https://github.com/Kotlin/KEEP/discussions/484). При расхождении
> верна английская; правки лучше вносить в обе сразу.

Документ объясняет все термины, которые встречаются в `kdm-renderer/docs`, в `KDM spec.md`
и в окружающем коде, не предполагая знакомства ни с Dokka, ни с Kotlin, ни с JVM.

**Как читать.** Разделы 1–7 упорядочены по зависимостям: каждый использует только те
термины, которые уже введены. Прочитайте их один раз по порядку, дальше пользуйтесь
алфавитным указателем в конце как справочником. Раздел 8 перечисляет термины, которые в
этом проекте действительно неоднозначны, — его стоит прочитать даже если всё остальное
пропускаете.

Считается известным: программирование в целом, что такое компилятор и синтаксическое
дерево, JSON и схемы, а также сама идея генератора документации. Всё остальное определено
здесь.

Английские названия оставлены в скобках там, где они и есть рабочий термин: в коде, в
конфигурации и в обсуждениях проекта используются именно они.

## 1. Предметная область

**Справочник API (API reference).** Сгенерированный сайт (или другой артефакт), который
документирует каждое публичное объявление библиотеки: его имя, сигнатуру и текстовое
описание. Отличается от написанного руками руководства: справочник API выводится из
исходного кода механически, поэтому его структура повторяет структуру кода. Пример —
`https://kotlinlang.org/api/core/`.

**Объявление (declaration).** Именованная сущность в исходном коде, на которую программист
может ссылаться: класс, функция, переменная, псевдоним типа. Единица документирования:
справочник API структурно — это список объявлений с прикреплённым к ним текстом.

**Сигнатура (signature).** Та часть объявления, которая определяет, как его вызывают или
используют: имя, типы параметров, тип результата, модификаторы, параметры типа. На странице
отображается строкой, похожей на код. Две функции могут совпадать по имени, но не по
сигнатуре.

**Документационный комментарий (doc comment).** Комментарий в исходном коде, написанный в
особом синтаксисе и предназначенный для извлечения генератором документации, а не для
читателя исходников.

**KDoc.** Формат документационных комментариев Kotlin. Основан на Markdown, пишется внутри
`/** ... */`, поддерживает блочные теги `@param`, `@return`, `@throws`, `@sample`, `@since`,
`@suppress`. Аналог Javadoc для Kotlin.

**Javadoc.** Формат документационных комментариев Java, а также название инструмента,
который превращает их в HTML, а также название той HTML-раскладки, которую этот инструмент
делает. Все три смысла встречаются в наших документах; различает контекст.

**Тег (tag).** Помеченный раздел внутри документационного комментария
(`@param имя описание`). Некоторые теги несут структурный смысл, на который реагирует
рендерер (`@sample` встраивает код, `@suppress` скрывает объявление); остальные — просто
текст с заголовком.

**Поверхность API (API surface).** Множество объявлений, которые библиотека предоставляет
своим пользователям, в противоположность её внутренней реализации. Что именно в неё входит —
решение конфигурации, а не факт: см. *видимость* (§ 2) и F-001 в реестре фич.

**Dokka.** Генератор документации для Kotlin от JetBrains. Читает исходники Kotlin (и Java),
выдаёт справочник API в HTML или других форматах. Предмет этого репозитория.

## 2. Словарь Kotlin

Только те понятия, которые влияют на модель документации. Это не учебник по Kotlin; сам язык
описан на `https://kotlinlang.org/docs/`.

**Пакет (package).** Пространство имён, записываемое точечным путём (`kotlinx.coroutines`).
Группирует объявления. В отличие от каталога, объявляется в самом файле, поэтому структура
пакетов и структура файлов не обязаны совпадать.

**Классификатор (classifier).** Обобщающий термин для объявлений, вводящих тип: class,
interface, object, enum class, annotation class, псевдоним типа. KDM использует именно это
слово (`KdClassifier`).

**Объект (object).** В Kotlin `object` объявляет синглтон — класс ровно с одним экземпляром,
объявленный и названный за один шаг. **Компаньон-объект (companion object)** — синглтон,
привязанный к классу; в нём держат то, что в других языках назвали бы статическими членами.

**Свойство (property).** Именованное значение у класса или на верхнем уровне: обращаются к
нему как к полю, но компилируется оно в методы доступа (геттер и, если изменяемое, сеттер).
Для документации различие принципиально: для читателя на Kotlin это одно объявление, а для
читателя на Java — до трёх. Ср. **поле (field)** — просто хранилище без методов доступа;
Kotlin показывает поля только через взаимодействие с Java.

**Расширяющая функция (extension function).** Функция, объявленная вне класса, но вызываемая
как его член: `fun String.shout() = uppercase() + "!"` вызывается как `"hi".shout()`.
Важно: *объявлена* она в каком-то пакете, а *принадлежит*, с точки зрения читателя, типу
`String`. Из этого расхождения выросли фича F-020 и пробел G-02: рендерер обязан показать
функцию на странице `String`, а для этого нужен индекс, построенный по всему модулю.

**Приёмник (receiver).** То, на чём объявлено расширение, — `String` в примере выше. У
расширения есть *приёмник расширения* (extension receiver), у члена внутри класса — неявный
*приёмник вызова* (dispatch receiver). В KDM это `KdReceiverParameter`.

**Контекстный параметр (context parameter).** Дополнительный неявный параметр, который
объявление требует в точке вызова помимо приёмника. Моделируется как `KdContextParameter`.

**Псевдоним типа (type alias).** Второе имя для существующего типа:
`typealias Handler = (Int) -> Unit`. Нового типа не вводит, поэтому документация должна
решить, показывать его как самостоятельное объявление, как тип-оригинал или и то и другое.
См. F-023.

**Элемент перечисления (enum entry).** Один из фиксированных именованных экземпляров
`enum class`. Структурно находится между объявлением и значением — поэтому обрабатывается
отдельно.

**Значимый класс (value class).** Класс, который компилятор там, где может, стирает до
единственного лежащего внутри значения. Важен потому, что его представление различается в
Kotlin-виде и в JVM-виде одного и того же API.

**Видимость (visibility).** Модификатор, определяющий, кто может ссылаться на объявление:
`public`, `internal` (виден внутри модуля компиляции), `protected`, `private`. Dokka
документирует настраиваемое подмножество — см. `documentedVisibilities`, F-001.

**Параметр типа, аргумент типа, вариантность, проекция.** Обобщённое объявление принимает
*параметры типа* (`class Box<T>`); место использования подставляет *аргументы типа*
(`Box<Int>`). *Вариантность* задаёт, можно ли использовать `Box<Sub>` там, где ожидается
`Box<Super>` (`out` / `in`). *Проекция* применяет вариантность в месте использования, а не в
месте объявления. Все четыре попадают в сигнатуры, поэтому все четыре обязаны быть в модели
структурой, а не заранее отрисованным текстом, — см. G-07. В KDM: `KdTypeParameter`,
`KdTypeProjection`.

**Nullability (допустимость null).** Система типов Kotlin различает `String` и `String?`.
В модели переносится как метаданные типа и работает за двоих: именно так KDM отличает
Java-овские `int`, `Integer` и `@NotNull Integer` (см. `KDM spec.md § Java`).

**Стандартная библиотека (stdlib).** Собственная базовая библиотека Kotlin (`kotlin.*`,
`kotlin.collections.*`). Упоминается постоянно, потому что почти любое документируемое API
ссылается внутрь неё, — и из-за этого межбиблиотечные ссылки становятся заботой первого
порядка, см. F-062.

### Мультиплатформенность

**Таргет (target).** Платформа, под которую компилируется проект на Kotlin: `jvm`, `js`,
`iosArm64`, `linuxX64` и так далее. В KDM: перечисление `KdTarget`.

**Исходный набор (source set).** Группа файлов исходного кода, компилируемых вместе для
одного или нескольких таргетов, с объявленной структурой зависимостей между группами.
У типичной мультиплатформенной библиотеки есть `commonMain` (компилируется под каждый
таргет) плюс `jvmMain`, `iosArm64Main`, … (каждый — под один), причём платформенные наборы
*зависят от* общего. Единица, которую Dokka настраивает и документирует, — исходные наборы,
а не таргеты.

**Мультиплатформенность (MPP).** Механизм Kotlin для компиляции одной кодовой базы под
несколько таргетов. Именно из-за него модели документации вообще нужен уровень-контейнер над
объявлениями: одно и то же объявление может существовать в нескольких исходных наборах с
разными деталями.

**expect / actual.** Механизм платформенной реализации общего объявления: `commonMain`
объявляет `expect class Foo`, а каждый платформенный исходный набор даёт `actual class Foo`.
Для читателя документации это *одно* API с вариациями по платформам; в исходниках это N+1
объявлений. Согласование этих двух взглядов — предмет `KDM spec.md § Variants of
declarations`, F-082 и Q-017.

`actual` может быть и *псевдонимом типа* для существующего платформенного типа — тогда
`expect`- и `actual`-стороны имеют по-настоящему разные модели. Это одна из заявленных причин,
почему KDM делает фрагменты уровнем-контейнером, а не полем внутри объявления.

**Android-флейвор / вариант.** Вариация одного модуля на этапе сборки в Android
(`debug`/`release`, product flavors). Структурно похожа и на expect/actual, и на
наследование, — поэтому `KDM spec.md` спрашивает, нельзя ли обобщить все три.

## 3. Словарь JVM

**JVM (Java Virtual Machine).** Среда исполнения, под которую Kotlin компилируют чаще
всего. Её понятия протекают в модель документации, потому что библиотеки на Kotlin
используют из Java и потому что исходники на Java можно документировать вместе с Kotlin.

**Класспас (classpath).** Список скомпилированных артефактов, доступных компиляции. Dokka
нужен, чтобы разрешать типы, на которые ссылаются, но которые не объявлены в разбираемых
исходниках.

**API против ABI.** *API* — то, под что программист пишет: имена, сигнатуры, типы. *ABI*
(двоичный интерфейс приложения) — то, что выставляет наружу скомпилированный артефакт,
включая специфичные для JVM факты, не имеющие смысла на уровне Kotlin: например, в какой
class-файл попала функция верхнего уровня. Различие существенно, потому что инструментам
Google нужна информация уровня ABI (имена файлов, multifile facade, `@JvmName`), которая
намеренно не входит в поверхность API Kotlin, — см. § 7 и Q-004.

**Отображаемый тип (mapped type).** Тип Kotlin, который компилятор отображает на тип JVM:
`kotlin.String` ↔ `java.lang.String`, `kotlin.collections.List` ↔ `java.util.List`.
Соответствие не всегда взаимно однозначно: `List.size` в Kotlin — *свойство*, а в Java —
*метод*. KDM хранит ссылку на отображаемое Java-объявление, чтобы документация могла
ссылаться внутрь JDK (`KDM spec.md § Java`).

**Аннотация с отображением (mapped annotation).** То же самое про аннотации: `@Deprecated`
в Java и `@Deprecated` в Kotlin — разные объявления с разными свойствами. В спецификации
проблема решена повышением устаревания до полноценного понятия вместо обработки его как
аннотации, — см. G-09.

**Синтетическое свойство (synthetic property).** Пара геттер/сеттер из Java, к которой
Kotlin позволяет обращаться как к свойству. Существует в Kotlin-виде Java-API, но
отсутствует в исходниках Java, — значит, модель должна уметь представлять объявление, у
которого нет объявления в исходном коде.

**Упаковка (boxing).** Различие JVM между примитивным `int` и объектным `Integer`. Видно в
документации, потому что `void foo(int)` и `void foo(Integer)` — разные перегрузки.

## 4. Конвейер Dokka

Раздел, на который опирается реестр фич. Dokka — многоступенчатый конвейер, в котором каждая
ступень заменяема плагином:

```
исходники ──▶ Documentables ──▶ (слияние) ──▶ Pages ──▶ Content ──▶ выходные файлы
          транслятор       трансформеры        транслятор        рендерер
```

**Плагин (plugin).** Единица расширения Dokka, упакованная в JAR на `pluginsClasspath`.
Собственная функциональность Dokka сама организована как плагины: `plugin-base` даёт
конвейер по умолчанию и HTML-вывод; `plugin-versioning`, `plugin-mathjax` и другие
добавляют фичи поверх.

**Точка расширения (extension point, EP).** Именованный слот, куда плагин может вставить
свою реализацию. Объявлены в `CoreExtensions` (ступени конвейера) и в `DokkaBase`
(HTML-специфичные и более мелкие слоты). Перечисление их — это то, чем занимается
`50-extension-points.md`: что вообще могут использовать третьи стороны.

**Documentable (документируемое).** Узел модели разобранного исходного кода в Dokka:
абстрактный класс `Documentable` и его подклассы, все с префиксом `D` — `DModule`,
`DPackage`, `DClass`, `DFunction`, `DProperty` и так далее. Это модель «структуры кода»: по
одному дереву на модуль, с объявлениями, их сигнатурами и разобранными документационными
комментариями. **KDM — замена этой модели**; в этом весь проект, одним предложением.

**Транслятор исходников в документируемые (source-to-documentable translator).** Ступень,
которая запускает анализатор Kotlin/Java и выдаёт `Documentable`-ы. Место, куда вместо этого
подключался бы производитель KDM.

**Трансформер документируемых (documentable transformer).** Ступень, переписывающая дерево
`Documentable`. В Dokka их ~18, и они делятся почти пополам на два вида — см.
`30-pipeline-surface.md`:
- *фильтры* выбрасывают объявления (по видимости, устареванию, `@suppress`, …);
- *построители индексов* добавляют информацию между объявлениями, которой не несёт ни одно
  объявление в одиночку (какие расширения применимы к типу, какие классы реализуют
  интерфейс).

Различие важно потому, что фильтры можно перенести на время рендеринга, если модель несёт
их входные данные, а построители индексов — нельзя: им нужен весь модуль целиком.

**Слияние документируемых (documentable merger).** Соединяет деревья отдельных исходных
наборов в одно, решая, что считать «одним и тем же объявлением» в разных наборах. Место, где
сегодня происходит согласование expect/actual.

**Страница (`PageNode`).** Узел модели структуры *выходного сайта*: по странице на модуль,
пакет, классоподобное, функцию и так далее. `RootPageNode` — корень дерева, `ContentPage` —
страница с содержимым. Заметьте: «страница» здесь — абстрактная единица вывода, не
обязательно один HTML-файл.

**Модель содержимого (`ContentNode`).** Независимое от формата описание того, что страница
*содержит*: группы, таблицы, блоки кода, ссылки, текст. Стоит между моделью объявлений и
конкретным форматом вывода. `ContentGroup` — составной узел. Именно из-за неё один конвейер
может выдавать HTML, Markdown и Javadoc: различается только финальный рендерер.

**Трансформер страниц (page transformer).** Ступень, переписывающая дерево
страниц/содержимого: добавляет ссылки на исходники, раскрывает `@sample`, объединяет
страницы перегрузок, навешивает значки версий.

**Рендерер (renderer).** Ступень, превращающая модель содержимого в выходные файлы.
`HtmlRenderer` — тот, который заменяет этот проект. Решение реализовать что-то в рендерере, а
не в трансформере, означает, что остальные форматы вывода молча этого не получат, — потому
`CLAUDE.md` и настаивает: выбирайте самый низкий слой, на котором выражается замысел.

**Провайдер сигнатур (signature provider).** Строит отрисованную сигнатуру объявления.
Читает конкретный набор полей модели; перечисление этих полей сразу даёт список требований к
модели (F-060).

**DRI (DokkaResourceIdentifier).** Идентификатор объявления в Dokka: `packageName`,
`classNames`, `callable`, `target`, `extra`. Используется для внутренних ссылок, для якорей
членов — а значит, и для URL каждой страницы и каждого якоря сгенерированного сайта.
Два следствия: DRI могут *сталкиваться* (отсюда `ClashingDriIdentifier`), и смена схемы
ломает все существующие внешние ссылки на документацию. KDM нужен эквивалент — пробел G-01,
вопрос Q-013.

**Провайдер расположений / резолвер (location provider / resolver).** Превращает DRI в URL.
Внутренние резолверы обрабатывают объявления текущей сборки; *внешние* — ссылки в
документацию других библиотек, включая цели в формате Javadoc.

**`package-list`.** Небольшой индексный файл, который Dokka публикует рядом со
сгенерированной документацией, со списком содержащихся в ней пакетов, — чтобы *другие*
проекты могли ссылаться внутрь, не имея её исходников. Существующий механизм межбиблиотечных
ссылок (F-062, G-06).

**Якорь (anchor).** Часть URL после `#`, адресующая конкретный член внутри страницы.
Выводится из DRI. Выглядит чисто оформительской деталью, а на самом деле входит в публичный
контракт URL — см. предупреждение в конце реестра фич.

**Препроцессор (`htmlPreprocessors`).** Точка расширения HTML-ступени, через которую
внедряют или переписывают вывод: так подключаются `plugin-mathjax` и `plugin-versioning`.

**Пузырёк исходного набора (source-set bubble).** Маленькая метка платформы («JVM», «iOS»)
рядом с объявлением в HTML-выводе, когда объявление существует в нескольких исходных
наборах. Название на уровне отрисовки для той мультиплатформенной вариативности, что описана
в § 2.

**Постдействие (post action).** Хук, который выполняется после завершения генерации.

**Многомодульная генерация (multi-module generation).** Документирование нескольких модулей
одним сайтом: каждый модуль генерируется отдельно, затем строится сводная страница и
подставляются межмодульные ссылки. За это отвечают `plugin-all-modules-page` и
`plugin-templating`, а `delayTemplateSubstitution` откладывает разрешение ссылок до сводного
шага.

## 5. KDM

**KDM (Kotlin Documentation Model).** Машиночитаемое сериализуемое представление
документированного API библиотеки на Kotlin: объявления, их сигнатуры и их документация в
стабильном публикуемом формате. Заменяет живущую в памяти модель `Documentable` артефактом,
который можно опубликовать, использовать инструментами кроме Dokka и отрисовать чем угодно.
Отслеживается в KEEP #484 и KTL-4815.

**KDP.** То же самое под прежним названием. Модель и проектные документы говорят KDM; пакет
`org.jetbrains.dokka.base.generation.kdp` и выходной каталог `<outputDir>/kdp/*.json` всё ещё
говорят KDP. Чистый дрейф названия, смысловой разницы нет, — см. Q-006.

**Иерархия вложенности.** Из проектного комментария в `KdModule.kt`:

```
project (kotlinx.coroutines)        <- только система сборки, в модели нет
 module (coroutines-core)           KdModule
  fragment (commonMain)             KdFragment
   package (kotlinx.coroutines)     KdPackage      | может быть общим для фрагментов
    [file (Job.kt)]                                 (сейчас не уровень модели)
     class (Job)                    KdClass        | может быть общим — expect/actual
      declaration (cancel)          KdDeclaration  | может быть общим — expect/actual
```

Текущая область — один модуль; `project` — понятие системы сборки и остаётся снаружи.

**Фрагмент (`KdFragment`).** Исходный набор как *контейнер* в модели: держит пакеты и хранит
собственные `name`, `dependsOn` (наборы, на которых он построен) и `targets`. Разместить
исходные наборы над объявлениями, а не помечать ими каждое объявление, — сознательное
проектное решение. Причины, из комментария в исходниках:

- `actual` в виде псевдонима типа означает, что `expect`- и `actual`-стороны могут иметь
  по-настоящему разные модели, — значит, одно объявление не может нести обе;
- expect/actual для классов ещё не стабилизирован, и модель не должна закладываться на то,
  как он будет развиваться;
- так организует объявления сам компилятор;
- для Android-флейворов можно построить все фрагменты один раз и потом *фильтровать*, получая
  разные выводы, а не перестраивать модель заново;
- это устраняет коллизии между одноимёнными объявлениями из разных исходных наборов, которые
  *не* являются парой expect/actual;
- информацию `targets` / `dependsOn` всё равно надо где-то хранить, и один раз.

Комментарий заканчивается словами «Maybe it will be a bad idea in the end :)» — относитесь к
решению как к предварительному. Это та структура, на которой стоят F-080…F-083 и G-12.

**Классы модели.** Все с префиксом `Kd`, лежат в
`kotlin-documentation/kotlin-documentation-model`, мультиплатформенные и размеченные
`kotlinx.serialization`. Основные семейства:

| Семейство | Члены |
|---|---|
| Контейнеры | `KdModule`, `KdFragment`, `KdPackage` |
| Объявления | `KdDeclaration` (sealed) → `KdClassifier` (`KdClass`, `KdTypealias`), `KdCallable` (`KdFunction`, `KdConstructor`, `KdVariable`) |
| Параметры | `KdParameter` (sealed) → `KdValueParameter`, `KdReceiverParameter`, `KdContextParameter`; плюс `KdTypeParameter` |
| Типы | `KdType` (sealed) → `KdClassifierType`, `KdFunctionalType`, `KdTypeParameterType`, `KdUnresolvedType`; `KdTypeProjection` |
| Идентичность | `KdClassifierId`, `KdCallableId` |
| Документация | `KdDocumentationNode` (sealed), `KdLinkReference`, `KdReturns`, `KdThrows` |
| Аннотации и константы | `KdAnnotation`, `KdAnnotationArgument`, `KdAnnotationArgumentValue`, `KdConstValue` |
| Внешнее | `KdExternalModule`, `KdExternalFragment`, `KdExternalLink` (в работе) |

**`KdUnresolvedType`.** Стоит выделить особо: модель явно представляет тип, который не
удалось разрешить, вместо того чтобы падать. Генерация документации обязана срабатывать и на
неполных входных данных.

**Кодирование (encoding).** `encoding.kt` даёт `encodeToJson`, `encodeToProtoBuf`,
`encodeToCbor` и `protoSchema()`, который генерирует схему ProtoBuf из модели. Какой формат
станет публикуемым — открыто: `KDM spec.md § Serialization format` взвешивает JSON (читаемый,
инструментарий есть), ProtoBuf (схема, чуть компактнее) и метаданные Kotlin (уже стабильны и
их совместимость поддерживают, но публичным API для внешних инструментов их никогда не
проектировали).

**Дедупликация (deduplication).** В мультиплатформенной библиотеке одно и то же объявление
существует во многих исходных наборах. Хранение его по одному разу на фрагмент — то, из-за
чего артефакт становится большим. Измерения из `KDM spec.md` для одного реального модуля:
~1 МБ, если каждый файл разбирается один раз (нынешний подход Dokka), ~30 МБ, если каждый
исходный набор разбирается полностью, и ~3 МБ с простой дедупликацией (хранится
идентификатор вместо повторного объявления). Поэтому идентичность объявлений (G-01) и
дедупликация (Q-017) сцеплены между собой.

**Внешний модуль (`KdExternalModule`).** Представление библиотеки, для которой KDM
*недоступен*, — в работе; нужно потому, что годами большинство целей ссылок его публиковать
не будет. Родной для KDM аналог `package-list` (G-06).

**Артефакт (artifact).** Здесь — опубликованный KDM-файл (или файлы) библиотеки. Приносит
вопросы, которых у чисто памятной модели не было: прямая и обратная совместимость, размер и
что делать потребителю, встретившему версию новее той, которую он понимает
(`KDM spec.md § Backward/forward compatibility guarantees`).

## 6. Анализ и сборка

Нужно, чтобы вносить вклад в репозиторий; не нужно, чтобы читать документы с требованиями.

**Анализ (analysis).** Ступень, разбирающая исходники Kotlin и разрешающая имена и типы, —
фронтенд компилятора, используемый как библиотека. У Dokka два взаимозаменяемых бэкенда за
`analysis-kotlin-api`.

**K1 / дескрипторы.** Старый фронтенд Kotlin. Его объекты разрешённых объявлений называются
*дескрипторами*. Реализация в Dokka: `analysis-kotlin-descriptors`.

**K2 / Analysis API / символы.** Актуальный фронтенд Kotlin, доступный инструментам через
*Analysis API* (часто сокращают до **AA**); его разрешённые объявления называются
*символами*. Реализация в Dokka: `analysis-kotlin-symbols`. Поскольку оба бэкенда должны
продолжать работать, тесты Dokka разделены на `testSymbols`, `testDescriptors` и
`testJavaSymbols` вместо одной задачи `test`.

**PSI (Program Structure Interface).** Абстракция синтаксического дерева от IntelliJ, общая
для IDE и для этих бэкендов анализа. Оттуда читаются исходники Java (`analysis-java-psi`).

**Композитная сборка (composite build).** Устройство Gradle, при котором несколько
независимых сборок соединяются в одну через `includeBuild`. В этом репозитории `build-logic`,
`dokka-integration-tests` и каждый ранер под `dokka-runners/` — отдельные сборки; поэтому
они и недостижимы из корня как пути задач `:dokka-runners:…`.

**Ранер (runner).** Обращённая к пользователю точка входа, которая запускает Dokka: плагин
Gradle (новый и классический), плагин Maven или CLI. Каждый выставляет свой DSL конфигурации
над одним и тем же `DokkaConfiguration`, — поэтому `20-config-surface.md` не будет полным,
пока ранеры не обследованы.

**Плагин-конвенция (convention plugin).** Скрипт сборки Gradle под
`build-logic/src/main/kotlin/dokkabuild.*.gradle.kts`, применяемый к подпроектам для общей
конфигурации: тулчейны, `explicitApi()`, публикация, разделение тестов.

**`explicitApi()`.** Режим компилятора Kotlin, требующий явных модификаторов видимости и
явных типов результата у публичных объявлений. Здесь включён для JVM-подпроектов вместе с
`allWarningsAsErrors`, — так что предупреждение ломает сборку.

**`apiDump` / файлы `.api`.** Закоммиченный текстовый дамп публичного API каждого модуля.
Любое изменение публичного API должно сопровождаться перегенерированным дампом
(`./gradlew apiDump`), иначе сборка падает. Делает изменения API видимыми на ревью.

**`@InternalDokkaApi`.** Маркер объявлений, публичных по техническим причинам, но не входящих
в поддерживаемое API.

## 7. Экосистема и заинтересованные стороны

**KEEP (Kotlin Evolution and Enhancement Process).** Публичный процесс предложения изменений
в Kotlin и его экосистему. KDM обсуждается в KEEP #484, — то есть часть проектных решений
принимается публично, а не в этом репозитории.

**Трекеры задач.** Префиксы YouTrack, встречающиеся в этих документах: `KTL-` (библиотеки
Kotlin; KTL-4815 — метазадача этого проекта), `KT-` (язык и компилятор Kotlin; KT-88346 —
сериализация документации, KT-88347 — наследование документации), `OSIP-` (инфраструктурные
проекты экосистемы Kotlin).

**Dackka.** Плагин Dokka от Google, которым генерируют документацию для библиотек Android и
Firebase. В `KDM spec.md § Java` описан как «a HUGE Dokka plugin». Значим непропорционально
своему размеру, потому что ему нужно то, чего KDM сейчас не обещает: документация для
потребителей на **Java** библиотек на Kotlin плюс факты уровня JVM/ABI (имена файлов,
multifile facade, `@JvmName`). Варианты Google: принять KDM, форкнуть Dokka или перейти на
Analysis API плюс ещё не существующее API для KDoc. В этом суть Q-004 и G-14.

**kotlinlang.org.** Место, где публикуется собственный справочник API языка Kotlin: на Dokka
с собственными шаблонами FreeMarker, — отсюда сторонний-но-свой потребитель `templatesDir`
(F-107).

## 8. Неоднозначные термины

Термины, которые в разных предложениях этого проекта означают разное. Стоит сверяться с этим
списком, прежде чем считать, что понял.

| Термин | Смыслы |
|---|---|
| **Модуль (module)** | (а) подпроект Gradle; (б) единица документации Dokka, `DModule`, по одной на раздел сгенерированного сайта; (в) `KdModule`, корень KDM; (г) *модуль компиляции* Kotlin, область действия видимости `internal`. Обычно (б)/(в), которые в основном совпадают. |
| **Фрагмент (fragment)** | (а) `KdFragment`, то есть исходный набор как контейнер KDM; (б) часть URL после `#`. § 5 против § 4. |
| **Documentable** | Тип модели Dokka (`Documentable`/`D*`). *Не* синоним «объявления» и не имеет отношения к `KdDocumented` из KDM. |
| **Документация** | (а) сгенерированный сайт; (б) содержимое документационного комментария, прикреплённое к объявлению (`KdDocumentationNode`). |
| **Страница (page)** | (а) `PageNode`, абстрактная единица вывода; (б) один HTML-файл. Соответствие не однозначное: наборы перегрузок сливают несколько объявлений на одну страницу. |
| **Модель (model)** | (а) модель `Documentable` в Dokka; (б) модель содержимого (`ContentNode`); (в) KDM. Три разные модели в одном конвейере. |
| **Javadoc** | (а) синтаксис документационных комментариев Java; (б) инструмент из JDK; (в) HTML-раскладка, которую этот инструмент делает и которую Dokka тоже умеет выдавать. |
| **KDM / KDP** | Одна и та же модель. См. Q-006. |
| **Target** | (а) таргет компиляции Kotlin (`jvm`, `iosArm64`); (б) `DRI.target` — на какую часть объявления указывает DRI. |
| **Исходный набор (source set)** | Группировка компиляции в Kotlin. В KDM называется *фрагментом*; в конфигурации Dokka и в HTML-выводе остаётся «source set». |
| **Фильтр (filter)** | (а) трансформер документируемых, выбрасывающий объявления на этапе сборки; (б) элемент интерфейса, скрывающий исходные наборы на отрисованной странице. F-001 против F-081. |
| **Индекс (index)** | (а) построенный трансформером справочник связей между объявлениями (расширения, наследники); (б) поисковый индекс HTML-сайта; (в) `index.html`. |
| **Паритет (parity)** | Определён отдельно в `00-method.md § 2` — не употребляйте здесь в вольном смысле. |

## Как поддерживать этот документ

- Термин попадает сюда, когда он встретился больше чем в одном документе или когда
  кому-то пришлось спросить, что он значит.
- Определения говорят, что эта вещь *есть* и почему она важна *для этого проекта*. Если
  определение можно скопировать дословно из документации Kotlin, лучше поставить ссылку туда
  и оставить здесь только следствие, специфичное для проекта.
- Новые термины добавляйте в тот повествовательный раздел, от которого они зависят, а затем
  в указатель. Внутри раздела сохраняйте порядок по зависимостям: никогда не употребляйте
  термин раньше, чем он введён.
- Когда термин на практике оказался неоднозначным, добавьте его в § 8, а не выбирайте
  «правильный» смысл в одиночку: неоднозначность обычно где-то несёт нагрузку.
- Эта копия — перевод. Правку по существу вносите сначала в [`glossary.md`](glossary.md),
  затем сюда, одним изменением.
